# 0001. `jira` CLI を Go で自前実装する（外部管理の TypeScript CLI を置き換える）

## 文脈

jira-dash は以前、検索・詳細取得・作成のたびに外部管理の TypeScript CLI をサブプロ
セスとして呼んでいた。この CLI はこのリポジトリの外で保守されており、起動コストが
支配的だった。

## 決定

`jira` CLI（本リポジトリの `cmd/jira`）と、jira-dash 本体が直接使う `internal/jira`
を Go で新規に書き、サブプロセス呼び出しをやめて in-process 化する。

## 理由

- Jira Cloud の REST API は Basic 認証（`base64(email:apiToken)`）を使う17個の
  プレーンな REST エンドポイントで、公開仕様から新規に書き直せる。外部 CLI の
  ソースを1行も持ち込む必要がない
- プロセス起動コストの実測: no-op 相当の呼び出しが 0.29s → 0.00s、`get` が
  1.49〜1.70s → 0.51〜1.22s に短縮した
- 移行範囲は使われている分だけに絞った。`release` の create/edit/list、
  `fields`、`comment` の edit/delete は**意図的に移植しなかった** — どこからも
  使われていなかったため
- 認証情報は移行前と**同じファイル・同じ形式**（`~/.config/jira-cli/credentials.json`
  、`apiToken` は base64、`JIRA_*` 環境変数も同名）で読む。ストアを2つ持たないことと、
  いつでも外部 CLI に戻せることの両方がこの1点にかかっている
- カスタムフィールドの id（`customfield_NNNNN`）はサイトごとに異なるため、
  ソースにハードコードせず `GET /field` を実行時に叩いて名前から解決する
- `scripts/verify-against-old-cli` を移行の関門とした。読み取り専用コマンド
  （`get` / `search` / `comment list` / `transitions`）の `-f json` 出力を新旧
  CLI で実際の課題に対して比較し、書き込み系は `--dry-run` の送信内容を比較した。
  このスクリプトは**外部 CLI がまだ端末に入っている間しか実行できない** — 今は
  入っていないため動かせない

## 結果（トレードオフ・限界）

- `POST /search/jql` は新エンドポイントで、`fields` の明示とトークンページングを
  要求する。旧 CLI と同じ結果になることは移行時の差分検証で確認済みだが、API 側の
  仕様変更を追随し続ける責務がこのリポジトリに移った
- ADF ⇄ Markdown の変換は完全ではない。旧 CLI も完全ではなく、移行時の差分検証で
  「同じ程度に不完全」であることまでは確認したが、両者が同じ箇所で不完全とは限らない
- カスタムフィールドの名前照合はサイトの言語設定に依存する。見つからない場合は
  空文字にして、使われた時点でエラーにする設計にしてあるので、静かに間違った id を
  使うことはない
- 書き込み系の検証は `--dry-run` の比較までで、本物の書き込みでの一致は運用の中で
  確認していくしかない
