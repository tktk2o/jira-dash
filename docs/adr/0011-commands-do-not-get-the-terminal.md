# 0011. 設定コマンドはデフォルトでターミナルを受け取らない

## 文脈

`keybindings.issues` のコマンドは、それまで例外なく `tea.ExecProcess` で走らせて
いた。この呼び出しはターミナルをコマンドに丸ごと渡し、終了後にダッシュボード全体を
再描画する。これが2つの不具合を同じ原因から生んでいた。

1. **キーを押すたびにちらつく** - 最も使う `jhd-claude-split … claude …` は
   `tmux split-window` を呼んで即終了するだけで、ターミナルを一切使わない。それでも
   ダッシュボードごと壊して描き直していた
2. **stderr が読めない** - `ExecProcess` がターミナルを握っている間にコマンドが
   何を出力しても、終了後の再描画がそれを上書きする。失敗はフッターの
   `a: exit status 1` としてしか見えず、何が悪かったのかを知る手段が無かった

## 決定

`Keybinding` に `terminal: true` を追加する。これを付けたキーだけが
`tea.ExecProcess` の経路を通る。付けていないキー（デフォルト）は普通の `tea.Cmd`
として実行し、stderr をキャプチャして `commandRanMsg` に載せる。

## 理由

- 設定にあるコマンドの大半 - tmux ペインを開く、ブラウザを開く、CLI で投稿する - は
  ターミナルを一切使わない。ターミナルを必要とするのは自前で画面を描くコマンド
  （エディタ、ページャ）だけで、それは稀な側なのでデフォルトを反転する価値がある
- `terminal: true` の無いコマンドは他の非同期処理（`fetchSection` など）と同じ形で
  実行できる: 自分のゴルーチンで走るので、失敗しても他のキーやスピナーの
  イベントループを止めない
- 失敗時に見せるのは `err.Error()`（`exit status 1` のような何も語らない文字列）
  ではなく、stderr の**最後の**空でない行にした。CLI は警告を先に、実際の
  エラーを最後に出すことが多いため、先頭行より最後の行の方が原因を言っている
  ことが多い
- ハングしたコマンドがキーを永久に死んだように見せないよう、`fetchTimeout`
  （既存の15秒の慣習）で `context.WithTimeout` + `exec.CommandContext` を使う。
  API 呼び出しと同じ上限を再利用しているだけで、コマンド専用の値を新設していない

## 結果（トレードオフ・限界）

- `terminal: true` を付け忘れたエディタ系コマンドは、TTY を取れずに落ちるか、
  ダッシュボードの下で操作不能になる。設定を書く側が判断する必要があり、
  自動判定はしていない
- stderr のスニペットは1行にトリムされる（`stderrSnippetMaxLen`）。長いスタック
  トレースの全体はフッターには出ない - 詳細を見る手段は今のところ無い
- `terminal: true` の有無で経路が分かれるのはテストで検証しているが、実TTY 無し
  で検証できるのは「どちらの経路を通ったか」までで、実際にターミナルを奪えているか
  自体はライブの tmux 上での確認に頼っている
