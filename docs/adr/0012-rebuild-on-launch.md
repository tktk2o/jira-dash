# 0012. バイナリは起動時に作り直す（watcher でも git hook でもなく）

## 決定

`~/.local/bin/jhd` と `~/.local/bin/jira` はバイナリではなく `scripts/jd` への
symlink にする。`jd` は起動名でどちらのパッケージかを決め、`.bin/` のバイナリより
新しい `*.go` / `go.mod` / `go.sum` があれば `go build` してから exec する。

## 背景

`go build -o ~/.local/bin/...` を手で打つ運用だと、打ち忘れが**新しいバグに化ける**。
実際に起きた事象:

```
~/.local/bin/jira-dash  ビルド 13:57
557f13e ターミナル明け渡しの停止   14:29   ← 入っていない
18cbfdc picker の fuzzy 絞り込み   14:45   ← 入っていない
```

この状態で「直したはずの画面のちらつきがまた起きた」「comment が失敗したかも」の
2件が報告された。前者は修正済みのものが再現したのではなく修正が入っていない
バイナリを動かしていただけで、後者は **stderr をフッターに出す修正が同じコミットに
入っていた**ため、失敗理由が読めなかった。症状が原因を隠す形になっていて、これは
デバッグの前提を壊す。

## 選択肢と却下理由

**file watcher（fswatch / launchd）** — 常駐を面倒見る対価が、保存ごとのビルド。
編集途中の壊れた状態でもビルドが走り、成功する最後のビルドがいつかは書き手の
保存タイミング次第になる。

**git hook（post-commit / post-checkout）** — 今回の事故はまさに防げるが、
**未コミットの編集を試している最中**は外れる。手で試す時こそ古いバイナリを踏む。

**`go run .`** — 常に正しいが毎回リンクのコストを払い、プロセスが一段増える分
シグナルと終了コードの扱いが余計になる。

## 実測

この方針が成立するかは「変わっていない時のコスト」で決まる。計測:

| | 実測 |
|---|---|
| mtime 比較のみ（変更なし） | 約 40ms |
| `go build`、内容変更なし | 0.38–0.41s |
| `go build`、実際に 1 ファイル編集 | 1.04s |

常用パスは 40ms なので体感に出ない。ビルドが走るのは実際に作り直す必要がある時だけで、
その 1.04s は jhd 自身の初回フェッチ（0.5–1.2s）と同程度、つまり元々待つ時間の範囲。

## 帰結

- ビルド失敗時は**直前のバイナリで走り続ける**が、警告を stderr に出す。道具が
  丸ごと使えなくなる方が困る一方、黙って古いコードを走らせるのはこのスクリプトが
  防ぎたかったことそのものなので、警告は省略しない。
- `JD_NO_AUTOBUILD=1` でビルドを完全に抑止できる。計測時と、ソースを壊している間に
  安定版で作業したい時のための逃げ道。
- ソースの位置は `realpath $0` から辿る。checkout のパスをどこにも焼き込まない。
- `.bin/` は生成物置き場（`.gitignore` 済み）。消しても 1 回のビルドで戻る。
